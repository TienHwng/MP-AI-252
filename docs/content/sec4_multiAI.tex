\section{Multi-Agent AI Pipeline Architecture}
\label{sec:multi-agent}

The \texttt{backend/HERA} subsystem implements the conversational
intelligence of H.E.R.A as a hierarchical multi-agent pipeline. Rather
than using a single model for every task, the backend separates
\emph{routing}, \emph{tool-centric control}, \emph{sensor analysis},
\emph{anomaly explanation}, and \emph{general conversation} into
specialized components. This choice is not only architectural; it is an
explicit latency and maintainability optimization for a resource-limited
student project.

\subsection{Why a Multi-Agent Backend}

The backend currently needs to solve four very different tasks:
\begin{itemize}
    \item map a short user utterance to one of four intents;
    \item execute a small number of deterministic device-control tools;
    \item explain live sensor readings in natural language;
    \item handle open-ended fallback conversation.
\end{itemize}

Placing all four tasks into one prompt creates three practical problems.
First, low-value requests such as ``turn on the LED'' would pay the full
latency cost of a larger model. Second, tool descriptions, sensor
context, and conversation rules would compete for the same prompt budget.
Third, debugging becomes difficult because reasoning errors, tool-call
errors, and conversational failures are coupled together.

The implemented solution is an \emph{orchestrator-specialist} topology:
a lightweight router classifies intent, then forwards the message to a
specialist agent that owns a much narrower system prompt and, when
needed, a constrained tool set. This is a pragmatic form of hierarchical
multi-agent design: it is simpler than peer-to-peer agent cooperation,
but it captures most of the latency and modularity benefits.

\subsection{Implementation Mapping to the Codebase}

The main execution path starts in
\texttt{backend/HERA/main.py}. The runtime wires together the
\texttt{LLMService}, \texttt{MQTTService}, \texttt{ToolRegistry},
four specialist agents, and the Telegram adapter. The orchestrator then
routes each \texttt{UserMessage} to one of four intent categories:
\texttt{device\_control}, \texttt{sensor\_query},
\texttt{anomaly\_query}, or \texttt{general}.

\subsection{Benchmark-Based Model Selection}
\label{sec:llm-benchmark-selection}

The codebase currently uses the Qwen2.5 family as the default local
stack: \texttt{qwen2.5:1.5b} for routing and cheap tool-centric tasks,
and \texttt{qwen2.5:7b} for the more explanation-heavy specialists.
This decision is supported by two engineering constraints:
\begin{enumerate}
    \item the project needs reliable local inference through Ollama;
    \item the system depends on structured output and tool/function
    calling rather than pure open-ended chat quality.
\end{enumerate}

\subsection{Specialist Responsibilities}

\paragraph{Orchestrator.}
The orchestrator is implemented in
\texttt{agents/orchestrator.py}. Its only job is to classify intent and
delegate. This narrow scope is why a small model is sufficient.

\paragraph{Device Control Agent.}
The device-control specialist is implemented in
\texttt{device\_agent.py}. It is the most tool-centric agent in
the backend and therefore benefits most from a reduced action space and
a parameterized tool schema.

\paragraph{Sensor Analysis Agent.}
The sensor specialist combines live MQTT state with concise natural
language interpretation. It benefits from a larger model because it must
explain numbers, thresholds, and current device state in human language.

\paragraph{Anomaly Expert Agent.}
The anomaly specialist currently mixes a deterministic rule layer with
LLM-generated explanation. This is reasonable as long as the LLM is used
for explanation only, not for safety-critical thresholding.

\paragraph{Chat Agent.}
The chat specialist is the fallback path for greetings, help messages,
and non-actionable requests. It is intentionally tool-free.

\subsection{Tool Schema Optimization}
\label{sec:tool-schema-opt}

The original backend exposed six device-control tools for only two
physical lights:
\begin{center}
    \small
    \texttt{turn\_on\_led}, \texttt{turn\_off\_led},
    \texttt{turn\_on\_neo\_led}, \texttt{turn\_off\_neo\_led}, \\
    \texttt{turn\_on\_all\_lights}, \texttt{turn\_off\_all\_lights}
\end{center}
This works, but it enlarges the tool vocabulary without increasing
capability.

The refactored design used in the backend collapses those tools into two
parameterized actions:
\begin{center}
    \small
    \texttt{turn\_on\_light(light\_target)} \\
    \texttt{turn\_off\_light(light\_target)}
\end{center}
where
\texttt{light\_target} is one of
\texttt{main\_led}, \texttt{neo\_led}, or
\texttt{all\_lights}.

makes future expansion to fans, relays, or indexed devices much cleaner.

\subsection{Practical Boundary Between LLM Logic and Deterministic Logic}

Reading the backend reveals an important design boundary. Some decisions
are naturally probabilistic and language-driven, while others should stay
deterministic:
\begin{itemize}
    \item Intent routing and user-facing explanation are good LLM tasks.
    \item Reading configurable safety thresholds from a JSON or config
    file is not an LLM task.
    \item Simple actuator execution is a tool task, not a reasoning task.
\end{itemize}

This distinction matters for the next chapter. Once customer-specific
temperature and humidity limits become configurable, threshold alerts
should be handled by deterministic rules. The TinyML model should be
moved to a different problem where learning genuinely adds value.

\subsection{Summary}

The H.E.R.A backend is strongest when treated as a layered system:
lightweight routing, constrained tool execution, larger-model
explanation, and deterministic rule handling where appropriate. The
benchmark tables justify the current choice of the Qwen2.5 family, while
the parameterized tool schema shows how the backend can be simplified
without weakening functionality.
